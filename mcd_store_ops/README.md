# mcd_store_ops · 门店日运营：报表清单 → 指标矩阵 → 看板

模拟"我是一家快餐门店的店长，每天要看哪些报表、怎么把它们变成能落到动作的矩阵"
的一整套可运行 package。

- 数据模型：一家门店每天真正在用的 **30 张表**（`docs/01`）
- 报表清单：店长一天的 **12 张日报表 + 4 张周报表**，每张写清"看完做什么"（`docs/02`）
- 指标字典：**32 项指标**，含公式 / 阈值 / 责任人 / 影响度 / 可控度（`config/metrics.json`）
- 矩阵方法：**5 种矩阵**，从"哪里出了问题"到"今天先做哪件"（`docs/03`）
- 看板规范：四层深度、六个家族、常见反模式（`docs/04`）
- 行动卡：12 张，红灯亮了先诊断再动手（`docs/05`）

核心链路（模拟器 / 指标引擎 / 矩阵 / 日报 / HTML 看板）**只用 Python 标准库**；
只有 Excel 导出需要 `openpyxl`。数据由模拟器生成（行级，不是拍脑袋的汇总值），
所以整条链路——从 POS 流水到看板上的一句"今天先做这件事"——是真的算出来的。

## 快速开始

```bash
cd mcd_store_ops
export PYTHONPATH=src

python -m mcdops.cli brief        # 班前会简报（终端，20 行）
python -m mcdops.cli excel        # 生成 Excel 工作簿（11 个 sheet，公式驱动）
python -m mcdops.cli all          # 生成 Markdown 日报 + HTML 看板 + Excel
python -m mcdops.cli reports      # 打印每日/每周报表清单
python -m mcdops.cli validate     # 校验指标字典 ↔ 数据字典 ↔ 报表 三者自洽
```

自己挖一层：

```bash
# 归因矩阵：服务速度达标率，按渠道拆
python -m mcdops.cli matrix speed_hit_rate channel

# 交叉矩阵：时段 × 渠道
python -m mcdops.cli cross speed_hit_rate daypart channel

# 换一天 / 换剧本（clean = 不注入问题，报表基本全绿）
python -m mcdops.cli brief --date 2026-08-15 --scenario clean

# 导出模拟数据为 CSV，拿去接自己的 BI
python -m mcdops.cli dump
```

`make all` 等价于上面的常用组合，见 `Makefile`。

LateNight          93.8%🟢  100.0%🟢    97.2%🟢   100.0%🟢    79.7%🔴

- **Delivery 一整列都红** → 结构问题（打包流程本身有毛病），加人没用，上报
- **Dinner 一整行都红** → 产能问题（晚市人不够），排班今天就能调

一个红灯，两个根因，两个责任人，两个时间尺度。
如果只看"服务速度达标率 76.6%"这一个数，这两件事会被混成一件，然后大概率都做不好。

## Excel 工作簿（11 个 sheet）

`make excel` 生成 `output/store_ops_package.xlsx`：

| Sheet | 内容 |
|---|---|
| 店长看板 | 18 项核心 KPI + 六家族灯 + 今天的三件事（公式动态排名） |
| 每日经营日报 | 一行一天 × 58 列，浅蓝=原子输入、白色=公式 |
| 优先级矩阵 | 影响度 × 可控度四象限，行动分与排名全是公式 |
| 时段矩阵 | 15 分钟 × 5 指标热力图 + 连续告警窗口 |
| 交叉矩阵 | 时段 × 渠道，三个指标各一张 |
| 归因矩阵 | 指标 × 维度，含量占比、该格预算、拖累度、累计占比 |
| 报表清单 / 行动卡 / 目标与口径 / 数据字典 / 使用说明 | 方法论与配置 |

**它和一份普通 Excel 模板的区别，在于阈值只存在一个地方。**
所有红黄绿都用 `INDEX/MATCH` 回查「目标与口径」，所以：

```
把食品成本率的绿线从 31% 改成 30%（只动两个格子）
  → 看板状态         黄 → 红
  → 超线带宽        0.15 → 1.22
  → 成本家族的灯      黄 → 红
  → 优先级行动分     0.08 → 1.39，排名 12 → 3
  → 看板「今天的三件事」第 3 项：迟到率 → 食品成本率
```

数字也不是贴进去的死值：日报里只有原子数（净销售、交易笔数、工时、废弃金额…）是输入，
客单价、各类成本率、SPLH、达标率全是公式，改一个输入右边一整行跟着重算。

`make verify` 会逐项核对工作簿里每个公式算出来的数是否等于指标引擎算出来的数
（当前 239 项全部一致）——`recalc` 报零错误只证明公式**能求值**，不证明它们**是对的**。

## 三个设计要点

这套东西和"把指标堆在一个 BI 页面上"的区别，主要在这三处。展开见 `docs/03`。

**① 一个指标只写一次公式，切片从外面传进来。**
全店、某时段、某渠道、"晚市 × 外送"这个交叉格，跑的是同一个函数。
矩阵不是另一套逻辑，只是同一个公式跑 N 遍——口径天然一致，
不会出现"同一个废弃率在三张报表里三个数"。

**② 排序用"拖累度"，不用指标值。**
外送废弃率 2.8%、堂食 0.9%，先动哪个？外送只占 3% 的量，压到 0 只省 0.08pp；
堂食占 70%，压 0.2pp 顶外送归零的两倍。所以归因矩阵的排序列是
"这一格拖了全店多少"，不是这一格本身有多难看。

**③ 严重度用阈值带宽标准化，不用相对偏差。**
迟到率目标 2%、实际 10.5%，相对偏差 −426%；速度达标率目标 90%、实际 76.6%，
相对偏差 −14.9%。按相对偏差排，迟到率天天第一——因为它基数小。
改用"越过绿线几个黄灯带宽"之后，不同量纲的指标才真正可比。

## 换成你自己的门店

三个文件，不用改代码：

1. `config/store_profile.json` —— 营业时段、渠道结构、品类、人力单价、设备清单
2. `config/metrics.json` —— 指标口径、目标与红黄线、责任人、影响度/可控度、行动卡
3. `src/mcdops/report.py` 的 `DAILY_REPORTS` —— 报表清单和每张表的"看完做什么"

改完跑一次 `python -m mcdops.cli validate`，它会检查：
每个指标有没有实现、引用的表在不在数据字典里、阈值方向对不对、
有没有指标不在任何一张报表里（"没人会看到的指标"）。

接真实数据时，把 `simulate.py` 换成你的数仓查询即可——
`MetricEngine` 只要一个 `{表名: [行字典]}` 的字典，不关心数据从哪来。

## 说明

门店数据均为模拟生成，用于演示报表与矩阵的**结构**。
指标口径、阈值、组织分工参考快餐连锁行业的通行做法，
具体数值需按各自品牌的实际标准替换，不代表任何特定企业的真实经营数据或内部标准。
