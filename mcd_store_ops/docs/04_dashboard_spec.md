# 04 · 看板设计：一般看哪些指标，怎么排

## 0. 一条原则

**看板不是指标越多越好，是"看的时长"分层。**

一个店长在高峰前只有 3 秒钟看一眼手机，班前会有 30 秒，午后复盘有 3 分钟，
周会有半小时。这四个时长对应四个屏，不是四个页签——是**同一块内容的四层深度**。

指标塞不下的时候，正确动作是"往下一层放"，不是"再加一行"。

| 屏 | 时长 | 回答 | 内容 |
|---|---|---|---|
| 第 0 屏 | 3 秒 | 今天是红是绿 | 4 个数 + 6 盏灯 |
| 第 1 屏 | 30 秒 | 今天做什么 | 优先级矩阵的三件事（带下钻结论） |
| 第 2 屏 | 3 分钟 | 为什么 | 时段矩阵 + 交叉矩阵 |
| 第 3 屏 | 复盘 | 全量 | 完整记分卡 + 14 天趋势 + 责任矩阵 |

`python -m mcdops.cli dashboard` 生成的 `output/dashboard.html` 就是按这四层排的。

---

## 1. 指标体系：六个家族，32 项

指标不按"部门"分，按**店长的六种担心**分。每一类都有一个"如果只能看一个"的代表：

| 家族 | 担心什么 | 如果只能看一个 | 项数 |
|---|---|---|---|
| **生意 SALES** | 今天钱够不够 | 销售达成率（不是净销售额） | 7 |
| **速度 SPEED** | 顾客等太久没有 | 服务速度达标率（不是平均时长） | 7 |
| **成本 COST** | 钱有没有漏掉 | 人时销售 SPLH | 6 |
| **品质与食安 QSC** | 会不会出事 | 关键温度点异常数 | 5 |
| **人员 PEOPLE** | 队伍撑不撑得住 | 出勤达成率 | 4 |
| **顾客 GUEST** | 顾客还来不来 | 顾客满意度 CSAT | 3 |

全量定义在 `config/metrics.json`。三点说明：

### 1.1 为什么速度看"达标率"而不是"平均时长"

平均值会骗人。平均 170 秒可能是「所有人都 170 秒」，
也可能是「八成人 120 秒、两成人 370 秒」——后者才是真正在流失顾客的那家店，
但两家店的平均值一模一样。

达标率（`speed_hit_rate`）直接回答"有多少比例的顾客体验是合格的"，
而且它天然可以按渠道用不同的目标线（外送 7 分钟、前台 2.5 分钟），一列数就能横向比。

平均时长仍然要留，但它的作用是**诊断**（分段看哪一段慢），不是**判分**。

### 1.2 为什么生意看"达成率"而不是"净销售额"

净销售额是绝对值，周二天生比周六低 25%。用固定目标去判红绿，
结果就是周一到周三永远红灯——三天以后没人再看这个颜色。

所以 `net_sales` 和 `guest_count` 的红绿阈值放得很宽（它们的绝对值只做"体量参照"），
真正判分的是 `sales_vs_forecast`，分母来自 `dim_sales_forecast`，逐日逐时段变化。

### 1.3 食安不是 KPI，是准入条件

`food_safety_score` 和 `critical_temp_fail` 在体系里的地位和其他 29 项不同：
它们不参与"权衡"。速度和成本可以互相让步（多排一个人，速度好了成本差了，这是决策），
食安关键项不行——一旦 fail，当天所有其他指标都不重要，先停产品再说。

看板上它们独立成一格，且**红灯不参与优先级排序**（不需要排，它是第 0 位）。

## 2. 第 0 屏：3 秒钟的四个数

只放四个，多一个都嫌多：

```
净销售 55,988    达成 97.9%    交易 1,564    客单 35.8
食品成本 31.2%   人工 13.2%    SPLH 215      废弃 1.1%
```

第一行是**生意**（做了多少），第二行是**效率**（赚没赚到）。
每个数配一条 14 天迷你趋势线——一个数没有趋势就没有意义，
"食品成本 31.2%"本身不说明任何事，"连续四天在爬"才是信息。

紧跟六盏家族灯，每盏灯带三个计数（绿/黄/红）和一句"这个家族里最该看的一项"。

---

## 3. 第 1 屏：30 秒钟的三件事

优先级矩阵的 top 3，每一件带四样东西：

1. **值 / 目标 / 超线几个带宽**
2. **象限和它的含义**（Q1 今天就做 / Q2 上报求援 / Q3 顺手做掉 / Q4 记录观察）
3. **责任人 + 行动卡编号**
4. **归因结论**：问题最集中在哪两三格，各拖累多少

第 4 点是这一屏和普通"异常列表"的分水岭。
普通看板告诉你"服务速度达标率 76.6% 红灯"；这一屏告诉你
"晚市 55.1%、外送 53.6%，其中外送全时段都差、晚市所有渠道一起塌"——
前者你还得再花十分钟去查，后者可以直接开会。

**为什么是三件，不是全部？** 一个班次能真正推动的改变就是两三件。
列十件等于一件都不做。剩下的黄灯在第 3 屏，不在这里。

## 4. 第 2 屏：3 分钟的"为什么"

### 时段矩阵（热力图）

行 = 指标，列 = 15 分钟，颜色 = 红黄绿。默认放五个：
销售达成率、速度达标率、得来速总时长、后厨制作时长、SPLH。

看法只有一条：**单点飘红是噪声，连成一片才是问题。**
`matrix.problem_windows()` 用"连续 ≥2 个时段非绿"来识别，直接给出
"17:00 → 19:45，12 个时段，最差 39.5%"这样的结论。

为什么是 15 分钟而不是小时？因为排班和备货的最小调整单位就是 15 分钟。
按小时看，一个 20 分钟的塌陷会被两边的好数据稀释掉，什么也看不见。

### 交叉矩阵（时段 × 渠道）

这是店长最常用的一步定位。同一张表能同时读出两种完全不同的问题：

- **某一列全红** → 结构问题（这个渠道的流程本身有毛病），加人没用
- **某一行全红** → 产能问题（这个时段人不够），排班能解决

两种问题的动作、责任人、时间尺度都不一样，混在一起就都做不好。
详细例子见 `docs/03` 第 5 节。

## 5. 第 3 屏：复盘用的全量

完整记分卡，每行：家族 / 指标 / 实际 / 目标 / 达标% / 超线带宽 / 状态 / 责任人 / 行动卡 / 14 天趋势。

关键是**排序不按红黄绿，按家族**。按状态排看着爽，但会让人只看红的；
按家族排才能看出"速度这个家族整体在退化"这种模式——
一个家族里三项同时转黄，比另一个家族里一项飘红严重得多。

底部放责任矩阵（M5）：谁 × 什么节奏 × 盯哪些指标。它一年也不变几次，
但它是"这个看板到底归谁管"的唯一答案，也是新店长交接时第一份要看的东西。

---

## 6. 三个常见的看板反模式

**① 把所有指标平铺在一屏**
结果是没有主次，红的绿的一样大，店长扫一眼什么也没记住。
修法：分层，每层限量（第 0 屏 4 个数、第 1 屏 3 件事）。

**② 只给数不给动作**
"废弃率 1.8%"下面没有任何东西。店长知道它高，但不知道高在哪、该找谁。
修法：每个指标绑定 `owner` 和 `playbook`，看板上直接显示。

**③ 目标写死不随日期变**
周二和周六用同一个销售目标、平日和节假日用同一个人工率目标。
红灯泛滥两周后，所有人开始无视颜色——这是看板死亡最常见的死法。
修法：量型指标用预测做分母（`sales_vs_forecast`），率型指标按 daypart 分别设阈值。

## 7. 刷新频率

| 层 | 刷新 | 为什么 |
|---|---|---|
| 第 0 屏的销售/交易 | 15 分钟 | 日内还来得及救 |
| 速度类 | 15 分钟 | 高峰中就要能看到，事后看没有意义 |
| 人力 / SPLH | 15 分钟 | 调班的决策窗口只有 30 分钟 |
| 废弃 / 保温 | 交接班（3 次/天） | 录入本身就是班次动作 |
| 食品成本率 | 日结 | 依赖盘点，日内算不准 |
| 顾客满意度 / 外卖评分 | 日批 | 数据来自外部，本来就有延迟 |
| 流失率 / 认证覆盖 | 周 | 日维度上是噪声 |

一个反直觉但重要的点：**不是所有指标都该实时。**
把食品成本率做成实时看板，只会让人盯着一个日内根本不准的数做无效决策。
刷新频率应该匹配**决策窗口**，而不是匹配技术能力。
