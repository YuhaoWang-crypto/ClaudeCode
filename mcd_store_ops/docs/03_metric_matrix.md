# 03 · 从报表到矩阵：怎么把一堆数字变成今天的三件事

报表回答「多少」。矩阵回答「**哪里**」和「**先做哪个**」。

一家门店一天能产出几万行数据、三十几个指标。店长真正的瓶颈从来不是"看不到数"，
而是"看到一堆红字，不知道先动哪个"。矩阵就是解决这一步的。

本文讲清楚五种矩阵各自解决什么、怎么算、以及三个最容易做错的地方。

---

## 0. 先划一条线：不是所有二维表都叫矩阵

矩阵之所以有用，是因为它满足三个条件：

1. **两个轴都是可行动的**。「指标 × 星座」不是矩阵，「指标 × 时段」是——因为时段对应排班。
2. **格子可排序**。你得能说出"这一格比那一格更该先动"，否则只是一张好看的表。
3. **排完序能落到人**。每一格背后有明确的责任人和动作，不然排序也没意义。

`config/metrics.json` 里的 `dims`、`impact`、`controllability`、`owner`、`playbook`
这五个字段，就是为这三个条件准备的。

---

## 1. 五种矩阵

| | 矩阵 | 两个轴 | 回答 | 代码 |
|---|---|---|---|---|
| M1 | 归因矩阵 | 一个指标 × 一个维度 | 问题出在哪个渠道 / 时段 / 品类 / 岗位 | `matrix.attribution()` |
| M2 | 时段矩阵 | 多个指标 × 15 分钟 | 一天里哪几段崩了 | `matrix.interval_grid()` |
| M3 | 交叉矩阵 | 维度 A × 维度 B | 钉到"晚市的外送"这种具体格子 | `matrix.cross()` |
| M4 | 优先级矩阵 | 影响度 × 可控度 | 今天先做哪一件 | `matrix.priority()` |
| M5 | 责任矩阵 | 责任人 × 频率 | 谁在什么节奏上盯什么 | `matrix.ownership()` |

M1–M3 是**诊断**，M4 是**决策**，M5 是**制度**。
一次完整的日复盘是 M4 → M1 → M2/M3：先定今天做什么，再往下找到具体是哪一格，
最后确认是不是某个时间窗口的连片问题。

---

## 2. 一个指标只写一次公式

矩阵最忌讳的实现方式，是给每张矩阵单独写一套 SQL。
指标一多，同一个"废弃率"在三张表里会算出三个数，然后所有人都不再相信看板。

本 package 的做法是：**公式只写一遍，切片由外面传进来。**

```python
def m_waste_pct(s, m):                     # s 是一个 Slice
    waste = sum(w["cost"] for w in s.rows("fct_waste_log"))
    return _div(waste * 100, _denominator_sales(s, m))
```

`Slice` 决定这次算的是全店、午市、汉堡品类，还是"晚市 × 得来速"这个交叉格。
于是所有矩阵都只是"同一个公式跑 N 遍"，口径天然一致。

对照关系：

```
全店记分卡      Slice(biz_date)                              → 一个数
M1 归因矩阵     Slice(biz_date, dim="channel", v=各渠道)      → 一列数
M2 时段矩阵     Slice(biz_date, dim="interval15", v=各时段)   → 一行数
M3 交叉矩阵     Slice(biz_date, dim="channel", v=..,          → 一片数
                      extra={"daypart": ..})
```

表里没有这个维度字段（比如 `fct_food_safety_check` 没有 `channel`），
`Slice.rows()` 返回空，指标算出 `None`，看板显示"—"。
**不适用**和**为零**必须分得开，否则会得出"外送渠道食安满分"这种荒谬结论。

## 3. 三个最容易做错的地方

### 3.1 分母口径：同一个指标有两种问法

「午市废弃率」有两个完全不同的意思：

- **切片口径**（`denominator: slice`）：午市废弃 ÷ 午市销售 → "午市自己控得好不好"
- **全店口径**（`denominator: store_day`）：午市废弃 ÷ 全天销售 → "午市拖了全店多少"

两个都对，但**用途不同，且不能混着排序**。

全店口径的好处是**可加**：

```
午市 0.61pp + 晚市 0.28pp + 早餐 0.11pp + … = 全店 1.10pp
```

归因矩阵要的正是这个——各格子加起来等于总数，才能说"午市贡献了一半的废弃"。
而切片口径的百分比加起来毫无意义（0.9% + 1.4% + 0.7% 不等于任何东西）。

本 package 的选择写在 `metrics.json` 的 `denominator` 字段里：
废弃率、食品成本率、千单投诉数用全店口径（它们要被归因）；
人工成本率、SPLH、客单价、速度类用切片口径（它们是各块自己的体检指标）。

### 3.2 排序依据：不能按指标值排，要按"拖累度"排

外送的废弃率 2.8%，堂食 0.9%。先动哪个？

看上去当然是外送。但外送只占 3% 的备货量，把它压到 0 也只省 0.08pp；
堂食占 70%，压 0.2pp 就顶外送归零的两倍。

所以归因矩阵的排序列不是指标值，是 **contribution（拖累度）**。三种算法：

| 指标类型 | 拖累度 | 例 |
|---|---|---|
| `aggregation: sum` 且有预测 | 预测 − 实际 | 晚市净销售少做了 3,200 元 |
| `denominator: store_day` | 值本身（已经可加） | 午市废弃占全店 0.61pp |
| 其余率型 | (目标 − 实际) × 该切片销售权重 | 外送速度差 36pp × 27% 权重 = 9.67 |

第三行那个"销售权重"是关键：它把"这块有多差"换算成"这块拖了全店多少"。
订单头里没有的维度（外卖平台、岗位、设备、区域），退化到各自的事实表按行数取权重
（见 `matrix._slice_weight`）。

### 3.3 格子的红绿：不能直接套全店阈值

这是 3.1 的直接后果，但几乎所有自建看板都会踩：**全店的阈值放到格子上就不成立了。**

两种失效方式：

| 指标类型 | 直接套全店阈值会怎样 | 正确做法 |
|---|---|---|
| 量型（净销售、交易笔数） | 晚市 4,761 元对着全店目标 62,000 → **整张矩阵一片红** | 改判"对该切片预测的达成率"（98% 绿 / 93% 黄） |
| 全店口径的率型（废弃率、千单投诉） | 午市 0.54pp 对着全店目标 0.8pp → **整张矩阵一片绿** | 阈值按量占比缩放：午市占 34% 的销售，它的废弃预算就是 0.8% × 34% = **0.27pp** |
| 其余率型（速度、人工率、客单价） | 没问题 | 照常判——这类目标本来就与切片大小无关 |

一片红和一片绿，信息量都是零。缩放之后才有东西可看：

```
废弃率 × 品类        全店 1.1%   目标 0.8%   贡献度口径：占全店百分点
品类           值   状态   对目标   拖累度  量占比
Burger       0.3%   🟢    +0.01    0.27    34%   ← 拖累度最大，但没超它那份预算
Chicken      0.2%   🟡    -0.08    0.24    20%
Dessert      0.2%   🔴    -0.15    0.21     8%   ← 只占 8% 的量，却吃掉两倍预算
Beverage     0.1%   🟢    +0.06    0.07    16%
```

汉堡的拖累度最大（0.27pp），但它占 34% 的量，属于"该它的"；
**甜品派只占 8% 的量却吃掉两倍预算，这才是真正失控的那一格。**
排序看拖累度，判色看缩放阈值——两列一起看，才能同时回答"影响多大"和"是否失控"。

各格的预算加起来正好等于全店目标，所以这套判色仍然是自洽的
（实现见 `matrix.scaled_metric()` 和 `matrix.cell_status()`）。

### 3.4 严重度：不能用相对偏差排优先级

迟到率目标 2%、实际 10.5%，相对偏差 **−426%**。
服务速度达标率目标 90%、实际 76.6%，相对偏差 **−14.9%**。

按相对偏差排，迟到率会稳居当天第一，天天如此——因为它的目标基数太小。
这是所有 KPI 看板最常见的排序陷阱。

正确做法是**用阈值带宽做标准化**：

```
severity = (实际越过绿线的距离) / |黄线 − 绿线|
```

- 迟到率：(10.5 − 3) / (8 − 3) = **1.51 个带宽**
- 速度达标率：(88 − 76.6) / (88 − 80) = **1.43 个带宽**
- 外卖评分：(4.7 − 4.14) / (4.7 − 4.5) = **2.80 个带宽**

量纲没了，基数影响没了，不同家族的指标终于可比。
`severity = 1.0` 意味着正好踩在红线上，这本身就是一句人能听懂的话。

## 4. M4 优先级矩阵：今天做什么

严重度只说明"差多少"，不说明"值不值得今天动"。还差两个乘数：

- **impact 影响度**：这个指标动一动，对生意和顾客的影响有多大
- **controllability 可控度**：店长今天真的能改变它多少

两个都写在 `metrics.json` 里，是**门店层面的常识判断，不是算出来的**。
比如原材料价格上涨导致的食品成本率上升，impact 高但 controllability 低——
店长再努力也压不动，硬压只会逼出偷工减料。

```
行动分 = severity × impact × controllability × (红灯 ? 2.0 : 1.0)
```

四象限用 impact / controllability 各 0.7 为界：

|  | 可控度 高 | 可控度 低 |
|---|---|---|
| **影响度 高** | **Q1 今天就做**<br>这就是班前会的内容 | **Q2 上报求援**<br>找营运经理/供应商/总部，别自己耗 |
| **影响度 低** | **Q3 顺手做掉**<br>交给值班经理清单化处理 | **Q4 记录观察**<br>别在今天的会上讲，进周复盘看趋势 |

**Q2 这一格是这张矩阵最大的价值。** 一个店长最容易的失败模式，
是把一整天耗在一个自己根本控不了的红灯上（比如平台配送时效、总部定价、设备等配件），
而放着三个自己一动就能好的黄灯不管。矩阵把这件事变成一句可执行的话：
"这个不归你，上报；今天你做那三个。"

## 5. 一次真实的诊断长什么样

以本 package 生成的示例日（2026-08-18）为例，完整链路：

**M4 优先级矩阵**给出今天的三件事：

```
1. 🔴 外卖平台评分 4.1 / 4.8   行动分 2.17   Q2 上报求援    店长
2. 🔴 服务速度达标率 76.6% / 90%  行动分 2.06   Q1 今天就做    值班经理
3. 🔴 迟到率 10.5% / 2%        行动分 1.02   Q3 顺手做掉    组长
```

**M1 归因矩阵**对第 2 项下钻：

```
服务速度达标率 × 渠道        全店 76.6%   贡献度口径：偏差 × 销售权重
渠道                 值    状态    对目标   拖累度  量占比
Delivery          53.6%    🔴    -36.4     9.67    27%
DriveThru         76.5%    🔴    -13.5     2.93    22%
FrontCounter      73.9%    🔴    -16.1     2.21    14%
MobileApp         83.7%    🟡     -6.3     0.60     9%
Kiosk             94.7%    🟢     +4.7    -1.35    29%
```

外送一家就占了拖累度的一半以上。注意 Kiosk 的拖累度是**负数**——它在帮全店拉分。

**M3 交叉矩阵**再钉一层：

```
服务速度达标率   时段 × 渠道
             FrontCounter   Kiosk  DriveThru  MobileApp  Delivery
Breakfast          92.3%🟢  100.0%🟢    97.2%🟢   100.0%🟢    73.9%🔴
Lunch              74.4%🔴   94.4%🟢    78.1%🔴    81.8%🟡    51.8%🔴
Afternoon          96.0%🟢  100.0%🟢    93.2%🟢    95.7%🟢    77.2%🔴
Dinner             50.0%🔴   88.3%🟢    47.2%🔴    68.1%🔴    24.8%🔴
LateNight          93.8%🟢  100.0%🟢    97.2%🟢   100.0%🟢    79.7%🔴
```

两个不同的问题被分开了：

- **横着看 Delivery 那一列**：全时段都红 → 这是**结构问题**（外送打包流程本身有毛病），
  不管忙不忙都慢，加人也解决不了。
- **横着看 Dinner 那一行**：所有渠道一起塌 → 这是**产能问题**（晚市人不够）。

**M2 时段矩阵**确认第二个判断：

```
服务速度达标率  连续告警：17:00 → 19:45（12 个 15 分钟，含红灯，最差 39.5%）
```

正好压在晚高峰上，连续 12 个时段，不是噪声。

**结论落到两个不同的动作**，交给两个不同的人：

1. 晚市 17:00–19:45 排班加人 / 调岗位 → 值班经理，今天就做（Q1）
2. 外送打包流程重设计 → 需要跨部门，店长上报（Q2），今天不耗在这上面

如果只看"服务速度达标率 76.6% 红灯"这一个数，这两件事会被混成一件，
然后大概率两件都做不好。**这就是矩阵的全部价值。**

## 6. 怎么落到你自己的系统里

上面所有矩阵，物理上只需要两张聚合表（见 `docs/01`）：

- `agg_metric_interval` —— 指标 × 15 分钟，撑起 M2
- `agg_metric_dim` —— 指标 × 维度 × 维度值，撑起 M1 / M3，`contribution` 就是排序列

M4 和 M5 不需要新表：M4 是对当日记分卡做一次排序，M5 完全来自 `metrics.json` 的配置。

落地顺序建议：

1. 先把 `metrics.json` 这张**指标字典**建起来，锁死口径、阈值、责任人。
   这一步不写任何代码，但它决定了后面所有事情。
2. 再建 `agg_metric_dim`，跑通一个指标的归因矩阵（建议从废弃率或速度达标率开始，
   它们下钻后的结论最直接可行动）。
3. 最后才做看板。**看板是最后一步，不是第一步**——
   先有能落到动作的口径，再谈可视化；反过来做，产出的一定是没人看的漂亮图表。
